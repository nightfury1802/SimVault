Motivation

Every Simscape modeling session produces .slx files that no future agent can find or reuse. Port names are inconsistent (omega_rpm vs w_shaft vs SpeedPS). Domain mismatches (thermal port → signal line) cause silent wiring errors. Fidelity variants (FEM ↔ averaged) are invisible to a search engine. The result: every agent rebuilds from scratch, makes the same mistakes, and produces one-off artifacts that never compound into a shared library.

SimVault solves this with five interlocking mechanisms:

Semantic Search

turbovec + BAAI/bge-small-en-v1.5 embeddings find the right component by description, fidelity, and analysis type even when port names differ.

BM25 Keyword Index

rank-bm25 over all graphify cache chunks gives exact keyword recall for model IDs, parameter names, and function names that embeddings miss.

Knowledge Graph

NetworkX tracks compatible ports, fidelity chains, and requires_input_from edges. Graphify KB holds session logs, pitfalls, and validated results.

Wire Validator

PASS / WARN / BLOCK for every proposed connection — catches domain mismatches, unit scale errors, and solver contract violations before any model_edit call.

Cross-Graph Links

358 discusses_model edges connect KB session nodes (pitfalls, validated results) to SimVault model nodes — unified by model ID mention.

Memory Decay

Four-tier confidence system with time-decay. Episodic facts fade over 90 days; procedural facts (model specs) are permanent. RRF fusion uses effective scores.

The Meta-Test (T9)
Agent A builds FEM_IM_FOC_MA.slx in a multi-agent workflow.
SimVault indexes it automatically via the Stop hook.
Agent B (future session) finds it via simvault_search and assembles a new model reusing that exact subsystem.

If T9 passes, every agentic build enriches the shared library — work compounds across sessions.

Architecture

SimVault comprises two graphs that live in separate stores but share a single turbovec embedding index. The Model Graph encodes port-level structure and compatibility of .slx subsystems. The KB Knowledge Graph encodes session history, pitfalls, and validated results extracted by graphify and LLM fact extraction. Cross-edges bridge the two.

Parser — extract_metadata.m

The only MATLAB component. Everything downstream is pure Python. The parser runs via matlab -batch invoked by simvault index, or manually in the MATLAB environment.

What it extracts

  • SHA-256 content hash of each .slx file — stored as source_hash for incremental indexing. Only changed files are re-processed.
  • Port names and directions from Inport, Outport, and Simscape physical port blocks.
  • SL2PS / PS2SL bridge detection — blocks named SL2PS_* or PS2SL_* are converted to named ports (e.g. SL2PS_Copper_Loss → port name Copper_Loss).
  • SimVault tags from the subsystem Description field (YAML-style inline: fidelity_tier: detailed, analysis_type: thermal, solver_contract: continuous).
  • Block and state counts for complexity metrics.

Tip — skip MATLAB
If you already have extracted JSONs (e.g. from a previous run), use simvault index <dir> --skip-matlab to skip the MATLAB step and run only the Python pipeline. Useful when MATLAB is unavailable or the .slx files haven't changed.

Canonicalizer — canonicalize.py

Maps raw port names to a fixed canonical vocabulary so that compatibility can be detected across models regardless of naming convention. Canonicalization is applied in-place to the extracted JSON files and also writes Markdown spec files to kb/models/.

How canonicalization works

Each port's original_name is tested against 20+ regex patterns (case-insensitive, first-match wins). When a match is found, the port receives:

  • canonical_name — the standard name used for all graph and validation operations
  • canonical_units — the standard unit for that physical quantity
  • unit_mismatch — true if the raw unit differs from canonical
  • scale_factor — the numeric gain (or offset string) needed to convert, if known
  • canonicalized — true if a match was found

Ports with no match get canonical_name: "" and canonicalized: false. They can still be wired, but the validator cannot check domain/unit compatibility for them.

Graph Builder — build_graph.py

Builds a networkx.DiGraph from canonicalized JSON files and saves it as simvault.graph.json in NetworkX node-link format.

Node types

subsystem node

One per indexed model. Carries: type="subsystem", fidelity_tier, analysis_type, solver_contract, block_count, state_count, source_hash, source_file, causal_summary.

port node

One per port in each subsystem. ID format: <subsystem_id>/ports/<canonical_name>. Carries all canonicalized port fields.

Edge types

Edge typeCountMeaningSource → Target
has_port129Ownership: subsystem owns this portsubsystem → port
compatible_with1410Two ports share the same canonical name, domain, and solver contract — safe to wire (bidirectional)port → port
fidelity_chain2Two subsystems represent the same component at different fidelity levels — same canonical port names, drop-in swapsubsystem ↔ subsystem
requires_input_fromvariesA thermal model has an unmatched loss input — identifies which EM subsystem should provide itthermal subsystem → EM subsystem

compatible_with matching rules

  1. Ports must belong to different subsystems
  2. domain must match (e.g. both "signal")
  3. Directions must be compatible: input↔output or bidirectional↔anything
  4. canonical_name must be identical and non-empty
  5. Solver contracts must be compatible (same, or one is "continuous")

fidelity_chain matching

Two subsystems are chained if their names share the same stem after stripping fidelity suffixes (_fem, _avg, _averaged, _simplified, _lookup, _nn, etc.) and their fidelity_tier tags differ. Example: PMSM_FEM (detailed) ↔ PMSM_avg (simplified).

Vector Store — vectors/index.py

Embeds model subsystem descriptions into store/kb.tq using a turbovec IdMapIndex. Model entries coexist with knowledge chunk entries in the same index — query_index() filters to source_type="model" after retrieval.

Embedding document construction

Each subsystem's embedding document is built from:

_build_doc(subsystem):
  causal_summary + model name + fidelity tier + analysis type +
  solver contract + canonical port names (sorted) + original port names
  → joined with " | ", embedded as a single string

Incremental update

Before embedding, build_index() checks chunk_map.json for each subsystem's source_hash. Subsystems whose hash is unchanged are skipped. This makes re-indexing after a partial model change fast.

Model ID resolution during query

Because the index holds both model (~28) and knowledge (~820+) embeddings, a simple top_k fetch will almost never return model entries at low ranks. query_index() fetches top_k × 50 candidates, filters to source_type="model", then applies fidelity/analysis/solver hard filters — equivalent to the old ChromaDB where clause.

Cross-Edge Linker — graph/link_entities.py

Draws discusses_model edges between the KB knowledge graph and SimVault model nodes. These cross-edges are the bridge that makes simvault_kb_query aware of which session logs, pitfall files, and code files discuss a specific model.

How edges are built

  1. Load all subsystem IDs from simvault.graph.json
  2. For each model ID, scan every node in graphify-out/graph.json
  3. A KB node matches if the model ID appears (case-insensitive) in its label or source_file
  4. One edge per unique (kb_node_id, model_id) pair — duplicates suppressed
Current state: 358 cross-edges across 28 model IDs
Sample: demo/build_FEM_IM_FOC.m → FEM_IM (conf=0.9)
Sample: demo/build_FEM_IM_OpenLoop_reference.m → FEM_IM (conf=0.9)

Cross-edges are not written to graphify-out/graph.json — they live exclusively in store/cross_edges.json and are loaded at query time by retrieval/unified.py.

Unified Query Engine — retrieval/unified.py

UnifiedQuery.search(query, k=10) is the single entry point for all KB queries. It classifies the query, routes to the appropriate retrieval strategies, fuses the ranked lists with RRF, and applies confidence decay before returning results.

Query classification

Query typeDetectionRetrieval strategy
relationshipKeywords: connect, relate, path, between, dependency, link, trace, chain, upstream, downstream, flow, pipeline…graphify BFS traversal first, then semantic (fallback)
model+kbA known SimVault model ID appears in the query (FEM_IM, PMSM_FEM, etc.)Semantic + BM25 + cross-edge results for the mentioned model IDs
kbDefault (no relationship keywords, no model ID)Semantic + BM25

Semantic search

Encodes the query with BAAI/bge-small-en-v1.5 and searches the turbovec index. Only entries with source_type="knowledge" are returned (model entries are filtered). Returns up to k×3 candidates from the index, then deduplicates by rel_path and loads text from the graphify cache file for the preview snippet.

BM25 index

BM25Index is built lazily at UnifiedQuery.__init__ from chunk_map.json. For each knowledge chunk entry, it loads the cache file and concatenates all node label fields into a tokenizable document. BM25Okapi from rank-bm25 scores documents by term frequency.

Why both semantic and BM25?
Semantic search excels at conceptual queries ("thermal losses in induction machine"). BM25 excels at exact recall ("lambda_ds pitfall", "T_ss=107.63"). Together they give recall that neither achieves alone. RRF fuses them without needing calibrated scores.

Reciprocal Rank Fusion (RRF)

Each result list is ranked. The fused score for a document is:

RRF_score(d) = Σ  1 / (k + rank_i(d))   for each list i that contains d
               i
               where k = 60  (standard constant)

Documents appearing in multiple lists get a significant boost. Documents in only one list get a lower contribution. The constant k=60 prevents extreme boosts for very-top-ranked items.

Memory Tiers & Confidence Decay

Every entry in the unified KB has a tier that determines its initial confidence and decay rate. The effective_confidence() function is applied during _apply_decay() to produce the final effective_score used for ranking.

TierInitial confidenceDecayAssigned to
working0.60Linear over 7 days, floor 5%Raw session observations (not currently used in pipeline)
episodic0.75Linear over 90 days, floor 5%All graphify cache chunks, session MD exports
semantic1.00None (permanent)PLAN.md decisions, validated facts
procedural1.00None (permanent)Model specs (vectors/index.py), MATLAB/Julia/Python source, skills

Decay formula

effective_confidence(node):
  if node.superseded_by: return 0.0      # overridden by newer fact
  if node.valid_until < now: return 0.0  # expired
  if decay_days is None: return base     # permanent tiers
  age = (now - created_at).days
  return base × max(0.05, 1.0 - (age / decay_days) × 0.5)

Tier inference rules

When tier is not explicitly set, memory/schema.py infers it from source_file:

  • SimVault/kb/models/, .jl, .m, .py, skills/ → procedural
  • PLAN.md, /decisions → semantic
  • store/sessions/, logs/session_ → episodic
  • Everything else → episodic (default)

Wire Validator — validator/validate_ports.py

Validates a proposed connection between two ports before any model_edit call. Returns one of three outcomes:

PASS

Connect directly. Domain, direction, units, and solver contract are all compatible.

WARN

Connect, but insert the specified bridge block first. Includes the exact block type and gain factor.

BLOCK

Do not connect. Incompatible domain, direction, or unknown unit conversion. Find an alternative path.

Validation rules (applied in order)

#RuleOutcomeExample
1 Domain mismatch — src.domain ≠ dst.domain BLOCK Simscape physical port → Simulink signal line
2 Direction conflict — not (input↔output) or bidirectional BLOCK output → output
3 Unit mismatch — units differ and conversion is known WARN rpm → rad/s: Gain block, factor 0.104720
3b Unit mismatch — units differ and no conversion known BLOCK Wb → A (no conversion)
4 Solver mismatch — different solver contracts WARN continuous ↔ discrete: Rate Transition block

Agent Assembly Workflow

Follow this exact sequence every time an agent builds or modifies a Simulink model:

1
DISCOVER — simvault_search
Natural language query, optionally filtered by fidelity/analysis/solver. Returns ranked subsystem IDs + compatible graph neighbors.
↓
2
CONTEXT — simvault_get_assembly_context
Pass ALL models you plan to connect. Get canonical port names, solver info, pre-validated wire pairs, and blocked pairs. Use these port names — never guess.
↓
3
VALIDATE — simvault_validate_wire
Call for any wire not in the pre-validated list. A WARN means connect but add the bridge block first. A BLOCK means find an alternative.
↓
4
BUILD — model_edit
Use canonical port names and solver config from step 2. Add bridge blocks for all WARN connections before connecting ports.
↓
5
RE-INDEX — simvault index <dir> --skip-matlab
Index the new model so future agents can find and reuse it. An un-indexed model is invisible to all future sessions.

EM motor + thermal model

simvault_search("FEM PMSM motor", fidelity_tier="detailed", analysis_type="torque_accuracy")

Known Pitfalls

Do not wire physical Simscape ports to Simulink signal lines
simvault_validate_wire returns BLOCK with "Domain mismatch". You need a PS-Simulink Converter (PS2SL) or Simulink-PS Converter (SL2PS) block in between. SimVault detects these patterns automatically when named PS2SL_* or SL2PS_*.
PMSM ≠ IM port names
The FEM_IM family exposes omega_slip_rads and uses isd_A/isq_A notation. The PMSM family does not have a slip port. Always query SimVault for the actual model ID — never port-name assumptions from a different machine type.
Add bridge block BEFORE connecting WARN ports
After a WARN, the connection is valid but requires a Gain or Rate Transition block. Add the bridge block first, then connect src_port → bridge_input and bridge_output → dst_port. Connecting the ports directly and adding the bridge after will produce an invalid wiring state.
Always re-index after building
An un-indexed model is invisible to all future agents and breaks the T9 meta-test. Run simvault index <dir> --skip-matlab immediately after any model_edit session. The Stop hook does this automatically if wired correctly.
Turbovec mixed-index retrieval
The kb.tq index holds both model (~28) and knowledge (~820+) embeddings. A plain top_k search will almost never surface model entries — they are diluted by the larger knowledge corpus. query_index() compensates by fetching top_k × 50 candidates and filtering. This is correct behavior, not a bug.
cross_edges.json is stale after new sessions
Cross-edges are rebuilt during simvault kb-update (step 4). If you bypass kb-update or add a new model ID without running the full pipeline, _cross_edge_results will not find edges for the new model until the next update.
